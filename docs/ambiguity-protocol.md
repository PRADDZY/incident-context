# Goal-oriented request supplement: preregistration

This bounded supplement measures whether feedback transfers to normal, goal-oriented incident requests whose diagnostic work is implicit. It must be reported alongside the initial study, never substituted for it. Improvement across checkpoints is a hypothesis; a rising curve is not guaranteed.

The independent request author worked only from the supplied task brief and general data-science guidance. The author did not inspect production code, incident tools or skills, existing datasets, execution results, selector behavior, or other agents' notes, and made no backend or model requests. No implementation-derived gold answers are included.

The frozen corpus contains 40 English requests: 20 training and 20 held out. Each split has 10 deployment and 10 provider requests, interleaved in the recorded order. Each service contributes five requests per family. Training uses only NorthstarCheckout (`northstar-checkout`; checkout/payments) and CedarDispatch (`cedar-dispatch`; dispatch/routing). Held-out requests use only JuniperSearch (`juniper-search`; search/discovery) and HarborLedger (`harbor-ledger`; ledger/billing). Service names and aliases do not cross splits. Checkpoints are 0, 5, 10, and 20 training tasks.

Deployment requests require establishing a regression, explaining the recent change, and considering a reversal. The brief stipulates one fixed simulated deployment incident per service: errors increased after retry budget changed from 3 to 0; current deployment is `dep-{serviceId}-20261115` and previous deployment is `dep-{serviceId}-20261114`. These are four underlying deployment fixtures, not 40 independent incidents. Repeated requests measure phrasing and service transfer within this narrow setting; they do not establish broad incident-response generalization.

Provider requests ask about real Cloudflare Workers public status. No outage state, incident presence, or causal link to the simulated app incident is prespecified. Provider observations can change with execution time. The independent observation grader will be reused; neither request wording nor any presumed selector strategy defines a gold tool sequence.

All 40 cases will be retained, including failures and unfavorable results. Report family-specific and split-specific outcomes as well as any aggregate result; do not treat repeated fixture observations as independent incident evidence. The dataset's raw-file SHA-256 is recorded next to it. No request wording, task membership, order, or intended semantics may be revised after execution starts. This document records a protocol only; no experiment execution or result is claimed.

Execution policy, recorded before execution: reuse the original fixed workflow and independently locked coverage/observation grader without changing planner, skills, priors, or request wording. Four canonical requests from the original corpus warm all four service memories before measurement, with no execution or feedback, followed by verification of untouched 1/1 priors in a fresh session. Measured passes freeze graph version and weights. The 160 retained cases comprise 20 ordered training attempts, four 20-case held-out graph checkpoints, and three 20-case final baseline passes (all catalog, lexical, and frozen graph). No model is called.

Checkpoints 0/5/10/20 count training attempts, separately from actual feedback updates. A plan HTTP 422 reporting `No known service alias found in the task`, `Service alias has no unique graph resolution`, or `Service has no unique graph resource` is a semantic resolution failure: preserve it as a failed case with null unavailable measurements, advance the attempt count, and submit no invented feedback. Returned runs update Beta counts only when an actual run and selected skill exist; a run with no selected skill is retained without feedback because no Beta key exists. Independent goal grades from actual training observations supply the feedback boolean; raw executor self-assessment remains separate. Every other HTTP failure, transport error, dataset integrity change, schema-byte mismatch, or freeze-audit change aborts the supplement and retains partial evidence. No retries or exclusions are permitted. All 20 held-out requests remain in each pass denominator, and held-out cases never receive feedback. Flat or worsening curves are retained.

The CLI writes fresh `evaluation/ambiguity-results.json` and `evaluation/ambiguity-resultsdetail.json` files and refuses to overwrite existing outputs. The report identifies this as a supplementary study and separates executor completion, independently graded observations, prerequisite coverage, and schema bytes. Detail includes per-family and per-split outcomes and attempt/feedback counts at every checkpoint. The raw corpus hash is `7f29df93c38efdf15d47fea66dbc958e5dfd5f26a5cc2257096f3b1f519da2f7`; the original corpus and its completed results remain unchanged.

Success metric, fixed before execution: supplementary goal success requires the original independent observation grader to pass on actual tool observations and the plan to resolve the authored service/resource correctly. Supplementary training feedback and curve/summary successes use this `observationSuccess` metric, because the production executor can infer a different family from goal-only wording and self-grade that different family. Raw `executorSuccess` remains a separate unrevised field and is reported alongside independent goal success. Only training executions affect feedback; held-out independent grades are measurements only. Default initial-study scoring and feedback remain based on its original executor metric.
